# Beta API deployment pipeline

`.github/workflows/beta-api.yml` tests and builds the API on a GitHub-hosted runner for every push to `main`. After those checks pass, it deploys on a repository runner installed on the Hetzner server. The deploy job stays skipped until the repository variable `BETA_DEPLOY_ENABLED` is set to `true`. A manual run from `main` uses the same checks and deploy steps.

The server runner connects outbound to GitHub. GitHub Actions does not need an SSH key or an inbound SSH rule for deployment. The Hetzner firewall can keep SSH restricted to your trusted IP. The deploy job never runs for pull requests, and the runner must be dedicated to this repository. This repository is currently public, so do not add pull-request workflows that target the server runner. [GitHub documents the risk of untrusted pull requests on self-hosted runners](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/manage-access).

## One-time setup

1. Create the Hetzner server, enable daily Backups, apply the firewall, and point the API DNS name at its Primary IPv4. Install Docker Engine with the Compose plugin, Python 3, and curl. A non-root account for the runner needs access to the Docker socket; membership in the `docker` group grants root-equivalent control of this server. Use this runner only for trusted deployments from `main`.
2. In the GitHub repository, open **Settings > Actions > Runners > New self-hosted runner**. Follow GitHub's current Linux x64 installation steps on the server, register it for this repository, add the custom label `woordenboom-beta`, and install it as a service. The workflow requires the `self-hosted`, `linux`, `x64`, and `woordenboom-beta` labels. [GitHub runner setup](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/add-runners) and [label rules](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/use-in-a-workflow).
3. Create `/etc/woordenboom/beta.env` from [`deploy/beta.env.example`](../deploy/beta.env.example). Set the final `API_DOMAIN`, independent random database and auth secrets, and working SMTP credentials. Keep this file outside the Git checkout. Make it root-owned, group-readable only by the runner's deployment group, and mode `0640`; the runner must be in that group. Create `/var/backups/woordenboom` outside the Git checkout with mode `0700`, writable by the runner. Restart the runner service after changing its groups. Never add either path to Git.
4. Create a GitHub environment named `beta` and restrict deployment branches to `main`. Protect `main` with a required review if others can push to the repository. Add a repository variable named `BETA_DEPLOY_ENABLED` with value `true` only after the runner, DNS, environment file, and backup directory are ready. No GitHub Actions secret is needed for the Compose deployment.
5. Run **Actions > Beta API > Run workflow** from `main` for the first deployment. Then verify `https://<API_DOMAIN>/readyz`, a real email login, practice, knowledge map, and daily progress on a device. Future pushes to `main` deploy after verification passes.

## What each deployment does

The workflow runs Go tests, validates the three release datasets, checks Compose configuration, and builds the API image. On the Hetzner runner, [`deploy/deploy-beta.sh`](../deploy/deploy-beta.sh) rebuilds the API, starts Postgres, saves a custom-format `pg_dump` under `/var/backups/woordenboom`, runs migrations, imports the pinned OpenTaal source on a fresh database, reruns the revision-checked release imports, starts the API and Caddy, and checks the HTTPS readiness endpoint. A failed command stops the deployment job. The existing API can be affected by a database migration before the new image starts, so plan releases during a quiet period.

The local predeploy dump is a recovery point for a bad migration. It does not replace encrypted off-server backups or a restore drill. Keep Hetzner daily Backups enabled and arrange an off-server `pg_dump` copy before inviting beta testers. If a code-only deploy fails, fix the issue and push a new commit. If a migration or import damaged data, restore a known-good database dump before redeploying; reverting code alone cannot reverse a schema change.
